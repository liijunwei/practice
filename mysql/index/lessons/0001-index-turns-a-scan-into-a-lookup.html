MySQL Indexes · Lesson 1

An index turns a scan into a lookup

The single most useful mental model in MySQL performance: without an index a query reads every row; with one it jumps straight to the rows it needs. Today you'll prove that with your own EXPLAIN.

The win

By the end you'll be able to (1) read the type column of an EXPLAIN, and (2) watch a query go from type=ALL (full table scan) to type=ref (index lookup) by adding a single index.

The mental model

A table is just a pile of rows in no particular order. To find every row where name = 'person_50000', MySQL with no index has one option: start at the first row and check every single row to the end. That's a full table scan — in EXPLAIN, type = ALL. The work grows in proportion to the table size.

An index is a separate, sorted copy of one (or more) columns, where each entry points back to the rows holding that value. Because it's sorted, MySQL can jump straight to the matching entries and follow their pointers — an index lookup (a "seek"). In EXPLAIN that's type = ref, or type = const when the match is on a primary key / unique column and returns exactly one row.

The type column is your scoreboard. Roughly, best to worst:

typeWhat it means
constExact match on a PRIMARY KEY / UNIQUE — one row, read once.
refIndex lookup on a non-unique index — all rows with that value.
rangeA span of the index (>, <, BETWEEN, IN).
ALLFull table scan — read every row. Usually the thing you're fixing.

Why this mattersWhen a production query is slow, the first thing you ask is: "what's the type?" If it says ALL, you've usually found the problem. MySQL docs — "How MySQL Uses Indexes"

Do it on your machine

Run each block in your mysql client. We'll make a table with 100,000 rows, query it with no index, then add one and watch the plan change.

1. Create the table

CREATE TABLE people (
  id   INT UNSIGNED     NOT NULL AUTO_INCREMENT,
  name VARCHAR(50)      NOT NULL,
  age  TINYINT UNSIGNED NOT NULL,
  PRIMARY KEY (id)
) ENGINE=InnoDB;

2. Fill it with 100,000 rows

SET SESSION cte_max_recursion_depth = 1000000;

INSERT INTO people (name, age)
WITH RECURSIVE seq (n) AS (
  SELECT 1
  UNION ALL
  SELECT n + 1 FROM seq WHERE n < 100000
)
SELECT CONCAT('person_', n), (n % 80) + 1
FROM seq;

3. Query a column that has no index

name has no index (only id, the primary key, does). Predict what type will be, then check:

EXPLAIN SELECT * FROM people WHERE name = 'person_50000';

You should see type = ALL, key = NULL, and rows ≈ 100000. MySQL has no shortcut — it will read the whole table to find one row.

4. Give it an index, then re-check

CREATE INDEX idx_name ON people (name);

EXPLAIN SELECT * FROM people WHERE name = 'person_50000';

Now the plan flips. Expected:

typekeyrows
no indexALLNULL~100000
with indexrefidx_name1

Same query, same answer — but now MySQL reads one row instead of 100,000.

5. Compare with the primary key

EXPLAIN SELECT * FROM people WHERE id = 50000;

This returns type = const: a unique, exact match on the primary key — the fastest lookup there is. That's your reference point for "optimal."

Optional: see real timingOn MySQL 8.0.18+ run EXPLAIN ANALYZE SELECT * FROM people WHERE name = 'person_50000'; before and after the index. It prints actual time and rows, not estimates.

Self-check

Answer from memory — don't scroll up.

Without an index, a query that filters on one column does a…

Right — no index means MySQL reads every row start to finish: a full table scan (type=ALL).

In EXPLAIN, the type value meaning "exact match on a unique / primary-key column" is…

const = one row, read once, from a PRIMARY KEY/UNIQUE equality. ref is the non-unique case.
