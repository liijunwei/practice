Three ways to silently disable an index

You can have the perfect index and still get type=ALL — because a small change to the WHERE clause hides the column's raw value from the index. Today: the three traps that do this, and the one-line fix for each.

The win

By the end you'll spot and fix, in any WHERE clause: (1) a function on the column, (2) a leading wildcard, and (3) an implicit type conversion — each of which silently turns an index lookup back into a full scan.

Trap 1 — a function on the column

The index stores created_at, not YEAR(created_at). When you wrap the column in a function, the sorted values the index holds no longer match what you're comparing, so MySQL can't use it.

-- no index (function hides the column)
EXPLAIN SELECT * FROM customers WHERE YEAR(created_at) = 2020;

-- index used (rewrite as a range over the raw column)
EXPLAIN SELECT * FROM customers
WHERE created_at >= '2020-01-01' AND created_at < '2021-01-01';

The fixMove the function to the other side of the comparison: compare the raw column to a computed boundary. Any function — YEAR(), LOWER(), DATE(), arithmetic like price * 2 — has the same effect.

Trap 2 — a leading wildcard

An index on a string is sorted from the start of the string. So LIKE 'abc%' (prefix) can use it, but LIKE '%abc' or LIKE '%abc%' (leading wildcard) cannot — MySQL has no idea where the match starts.

-- no index (leading wildcard)
EXPLAIN SELECT * FROM customers WHERE email LIKE '%example.com';

-- index used (prefix match)
EXPLAIN SELECT * FROM customers WHERE email LIKE 'user%';

The fixSearch a prefix, not a suffix. If you genuinely need to match the end of a string, the usual tricks are a FULLTEXT index or storing a reversed copy of the column — both out of scope for now, but worth knowing exist.

Trap 3 — an implicit type conversion

Comparing a string column to a number forces MySQL to convert the column's values to numbers — row by row — so the index is bypassed. This is the sneakiest trap because the query looks fine.

-- no index (VARCHAR column compared to a number)
EXPLAIN SELECT * FROM customers WHERE phone = 5550000250;

-- index used (compare to a string, matching the column type)
EXPLAIN SELECT * FROM customers WHERE phone = '5550000250';

The fixCompare a column to a literal of the same type. A string column gets a quoted string; an integer column gets a number. The danger is only one direction: string column + number literal.

Do it on your machine

1. Create and fill the table

CREATE TABLE customers (
  id         INT UNSIGNED NOT NULL AUTO_INCREMENT,
  email      VARCHAR(120) NOT NULL,
  phone      VARCHAR(20)  NOT NULL,
  created_at DATETIME     NOT NULL,
  PRIMARY KEY (id),
  KEY idx_email (email),
  KEY idx_phone (phone),
  KEY idx_created (created_at)
) ENGINE=InnoDB;

SET SESSION cte_max_recursion_depth = 1000000;
INSERT INTO customers (email, phone, created_at)
WITH RECURSIVE seq (n) AS (
  SELECT 1 UNION ALL SELECT n + 1 FROM seq WHERE n < 500
)
SELECT
  CONCAT('user', n, '@example.com'),
  CONCAT('555', LPAD(n, 7, '0')),
  TIMESTAMP('2020-01-01') + INTERVAL n HOUR
FROM seq;

All three traps produce the exact same symptom you met in Lesson 1: type=ALL, key=NULL — even though a perfectly good index exists. That's why "which index exists?" is only half the question; "does this WHERE let the index see the column?" is the other half.

Self-check

Answer from memory — don't scroll up.

Which can use an index on created_at?

Only the raw column on the left of a comparison can use the index; wrapping it in YEAR() or DATE() hides it.

Which LIKE can use an index on email?

A trailing wildcard ('user%') matches a prefix, which the sorted index can serve. A leading wildcard cannot. (LIKE 'user' also works, as an exact match.)

On a VARCHAR phone column, which comparison uses the index?

Comparing to a quoted string matches the column type, so the index is used. A number forces a per-row cast of the column.
