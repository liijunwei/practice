MySQL Indexes · Lesson 4

An index can answer the query by itself

If the index already holds every column the query needs, MySQL never has to read the table row at all. That's a covering index — Using index in EXPLAIN. And in InnoDB, every secondary index secretly carries the primary key, so it covers more than you'd guess.

The win

By the end you'll (1) define a covering index in one sentence, (2) tell Using index from Using index condition in EXPLAIN, and (3) explain why SELECT * defeats coverage.

The model: a phone book with the number printed in it

So far an index points you to a row, then you still go fetch the row. But imagine a phone book where each entry also prints the phone number right there. To look up a number, you never open the main directory — you read the phone book alone.

A covering index is exactly that: an index that contains every column the query needs — across SELECT, WHERE, ORDER BY, and GROUP BY. MySQL can answer the whole query from the index and skip the table entirely. In EXPLAIN's Extra column, this shows as Using index.

Here's the part that surprises people: in InnoDB, a secondary index always stores the primary key at the end of every entry. An index on (name) is really (name, id) where id is the primary key. So an index "contains" one more column than you declared.

The trade-offWhen the query is not covered, MySQL reads the index to find rows, then does a second read of the actual table row for the missing columns. That second read is what covering saves you — it's a real win on wide tables or big result sets. MySQL docs — "Covering Indexes"

Do it on your machine

1. Create and fill the table

CREATE TABLE people (
  id   INT UNSIGNED     NOT NULL AUTO_INCREMENT,
  name VARCHAR(50)      NOT NULL,
  age  TINYINT UNSIGNED NOT NULL,
  PRIMARY KEY (id),
  KEY idx_name (name)
) ENGINE=InnoDB;

SET SESSION cte_max_recursion_depth = 1000000;
INSERT INTO people (name, age)
WITH RECURSIVE seq (n) AS (
  SELECT 1 UNION ALL SELECT n + 1 FROM seq WHERE n < 500
)
SELECT CONCAT('person_', n), (n % 80) + 1
FROM seq;

2. Compare three SELECT lists against the same WHERE

-- only `name` → everything's in the index
EXPLAIN SELECT name FROM people WHERE name = 'person_250';

-- `name` + `age` → age is NOT in the index
EXPLAIN SELECT name, age FROM people WHERE name = 'person_250';

-- `id` + `name` → id is secretly in the index
EXPLAIN SELECT id, name FROM people WHERE name = 'person_250';

Expected Extra column:

SELECT listExtraWhat it means
nameUsing indexCovered — read the index only, no table row.
name, ageUsing index conditionNeeds age → must read the table row.
id, nameUsing indexCovered — id lives in the index too.

The middle row is the trap: same WHERE, same index — but age isn't in the index, so MySQL has to go read the table row for it. The Extra column flips from Using index to Using index condition (an "index condition pushdown": it filters against the index, then reads the row).

Why SELECT * hurtsSELECT * asks for every column, so the index rarely covers it — even if the WHERE is perfect. When a query is slow, a narrower SELECT list (only the columns you actually need) is often what turns it into a covered, table-free read.

Self-check

Answer from memory — don't scroll up.

A covering index is one that…

Covered means every column the query touches — SELECT, WHERE, ORDER BY, GROUP BY — is present in the index, so no table read is needed.

In InnoDB, a secondary index also secretly stores…

Every secondary index entry ends with the primary key, so the PK is available "for free" in every index.

Which EXPLAIN Extra value means "covered, no table read"?

Using index = the index alone answers the query. Using index condition means it still needs the table row.
