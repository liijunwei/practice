MySQL Indexes · Lesson 7

A join is many lookups — index the join key

MySQL joins with a nested loop: it reads the first table, and for each row looks up the second table by the join key. If that join key has no index, it scans the second table once per row — and the work multiplies. The same type column you met in Lesson 1 now reads across multiple tables.

The win

By the end you'll (1) read a two-table EXPLAIN, (2) know eq_ref/ref are good and ALL on the inner table is catastrophic, and (3) state that a join key needs an index exactly like a WHERE column does.

The model: a nested loop

Joining customers and orders on orders.customer_id = customers.id is, to MySQL, this loop:

for each row in customers:            -- the "driving" table
    find every order with customer_id = row.id   -- a lookup

That inner "find every order" is just a lookup on orders.customer_id — exactly like a WHERE filter. So the join key needs an index for the same reason a filtered column does. Without one, each of the N customers forces a full scan of the M orders → N × M work. With one, it's N cheap lookups.

The type column now describes each table's access in that loop:

type (joined table)Meaning
eq_refLookup on a PRIMARY KEY / UNIQUE key — exactly one row per lookup. Best.
refLookup on a non-unique index — several rows per lookup.
ALLNo index → full scan of that table for every row of the outer one. The thing you're fixing.

Do it on your machine

1. Create and fill two tables

CREATE TABLE customers (
  id   INT UNSIGNED NOT NULL AUTO_INCREMENT,
  name VARCHAR(50)  NOT NULL,
  PRIMARY KEY (id)
) ENGINE=InnoDB;

CREATE TABLE orders (
  id          INT UNSIGNED NOT NULL AUTO_INCREMENT,
  customer_id INT UNSIGNED NOT NULL,
  amount      INT UNSIGNED NOT NULL,
  PRIMARY KEY (id)
) ENGINE=InnoDB;

SET SESSION cte_max_recursion_depth = 1000000;
INSERT INTO customers (name)
WITH RECURSIVE seq (n) AS (
  SELECT 1 UNION ALL SELECT n + 1 FROM seq WHERE n < 50
)
SELECT CONCAT('customer_', n) FROM seq;

INSERT INTO orders (customer_id, amount)
WITH RECURSIVE seq (n) AS (
  SELECT 1 UNION ALL SELECT n + 1 FROM seq WHERE n < 500
)
SELECT (n % 50) + 1, (n * 17) % 1000 + 1
FROM seq;

2. Join with no index on the join key

EXPLAIN SELECT c.name, o.amount
FROM customers c
JOIN orders o ON o.customer_id = c.id;

Notice the second row (orders) shows type=ALL. Every one of the 50 customers forces a scan of all 500 orders — about 25,000 reads where 500 would do.

3. Index the join key, re-check

CREATE INDEX idx_cust ON orders (customer_id);

EXPLAIN SELECT c.name, o.amount
FROM customers c
JOIN orders o ON o.customer_id = c.id;

Now orders flips to type=ref, key=idx_cust — a cheap lookup per customer instead of a scan. Same join, no change to the SQL, just the missing index.

4. See eq_ref by joining onto the primary key

EXPLAIN SELECT o.amount, c.name
FROM orders o
JOIN customers c ON c.id = o.customer_id;

Here the joined table customers is matched on its PRIMARY KEY (c.id), so it shows type=eq_ref — one row per lookup. That's the reference point for an optimal join.

Reading a plan top to bottomEach row of EXPLAIN is one table in the loop, listed in the order MySQL processes them. Read it as a story: the top table drives, the next table is looked up per row, and so on. The rows column is per-table — multiply across the join to estimate total work. Self-check

Answer from memory — don't scroll up.

In a join, eq_ref means a lookup on…

eq_ref = the join key is PRIMARY KEY/UNIQUE, so each lookup returns exactly one row — the best join access.

The worst type for a joined table is…

ALL means a full scan of that table for every row of the outer one — the work multiplies across the loop.

To speed up a JOIN, you index the…

The inner lookup is on the join key, so that's what needs an index — exactly like a filtered column.
