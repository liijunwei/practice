MySQL Indexes · Lesson 6

Design the index: equality, then range, then sort

You now know how indexes work and how they break. Here's the decision procedure for building one: list your equality columns, then the range column, then the sort column — in that order. And let cardinality tell you which columns are worth indexing at all.

The win

By the end you'll (1) read SHOW INDEX Cardinality to judge a column's selectivity, (2) order a composite index equality→range→sort, and (3) know when one index serves several queries and when you need a second one.

Selectivity: some columns are worth more than others

A column's selectivity is how much it narrows the search: a value that matches few rows is selective. It's measured by cardinality — the number of distinct values. High cardinality = selective. A status column with 3 values filters nothing useful; a customer_id with 50,000 values filters a lot. MySQL shows its estimate in SHOW INDEX:

SHOW INDEX FROM orders;

Look at the Cardinality column. For a low-cardinality column (like status), an index is barely better than a full scan — MySQL may even skip it. Save your indexes for columns that actually divide the data.

The recipe

Given a query, choose columns in this order:

  1. Equality columns — every col = ? in the WHERE. Put them first. Among equals, most selective first is a tie-breaker, not a law.
  2. The range column — the single >/</BETWEEN/LIKE 'x%'. Next, because (Lesson 3) nothing after it can narrow further.
  3. The sort columns — whatever's in ORDER BY / GROUP BY, last, so the rows come out already sorted (Lesson 2).
  4. Stop. Don't add columns used only in SELECT unless they'd make it a cheap covering index (Lesson 4).

One index, many queries

An index's value comes from its prefixes. Index (a, b) already serves WHERE a = ? and WHERE a = ? AND b = ? — so a separate index on (a) alone is redundant. But it can't serve WHERE b = ?. So:

You query by…Build…
a, and a,b(a, b) — one index covers both.
b alone (and not a)a second index (b).
a, and b alone(a, b) plus (b).

Always verifyThese are rules of thumb, not guarantees. Design the index, then run EXPLAIN and confirm you see ref/range and no Using filesort. The plan is the truth.

Do it on your machine

1. Create and fill an orders table

CREATE TABLE orders (
  id          INT UNSIGNED NOT NULL AUTO_INCREMENT,
  customer_id INT UNSIGNED NOT NULL,
  status      VARCHAR(20)  NOT NULL,
  created_at  DATETIME     NOT NULL,
  amount      INT UNSIGNED NOT NULL,
  PRIMARY KEY (id)
) ENGINE=InnoDB;

SET SESSION cte_max_recursion_depth = 1000000;
INSERT INTO orders (customer_id, status, created_at, amount)
WITH RECURSIVE seq (n) AS (
  SELECT 1 UNION ALL SELECT n + 1 FROM seq WHERE n < 10000
)
SELECT
  (n % 500) + 1,                                   -- 500 distinct customers
  ELT((n % 3) + 1, 'paid', 'pending', 'shipped'),  -- only 3 statuses
  TIMESTAMP('2020-01-01') + INTERVAL n MINUTE,
  (n * 17) % 1000 + 1
FROM seq;

2. Look at cardinality

CREATE INDEX idx_cust_status_created ON orders (customer_id, status, created_at);

SHOW INDEX FROM orders;

Find idx_cust_status_created. Its Cardinality should read roughly 500 for customer_id, 3 for status, and ~10000 for created_at. That's selectivity in a nutshell: customer_id divides the data, status barely does.

3. Apply the recipe to a real query

SELECT * FROM orders
WHERE customer_id = 77 AND status = 'paid'
ORDER BY created_at DESC
LIMIT 10;

Equality: customer_id, status. Sort: created_at. So the index is (customer_id, status, created_at) — exactly what we built. Confirm it:

EXPLAIN SELECT * FROM orders
WHERE customer_id = 77 AND status = 'paid'
ORDER BY created_at DESC
LIMIT 10;

You should see type=ref, key=idx_cust_status_created, and no Using filesort — the rows for customer 77 with status 'paid' come out already ordered by created_at.

Self-check

Answer from memory — don't scroll up.

For WHERE a = ? AND b > ?, which column goes first?

Equality columns always come before the range, so the range can narrow within the equality's slice.

High cardinality on a column means…

Cardinality = count of distinct values. Many distinct values → each value matches few rows → selective.

An index (a, b) already serves which query?

The leftmost prefix a is served by (a, b). Queries on b alone need a separate index.
