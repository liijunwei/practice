MySQL Indexes · Lesson 3

A range stops the prefix

A composite index (a, b) handles equality on a, then a range on b — but once you hit a range, every column after it can no longer narrow the search. The proof is key_len: it tells you exactly how many columns of the index MySQL is actually using.

The win

By the end you'll (1) state the range rule in one sentence, (2) read key_len to count how many index columns a query uses, and (3) predict — before EXPLAIN — whether a > ? AND b = ? uses both columns or just a.

The model: equality first, range second

Back to the phone book, sorted by (last_name, first_name). Compare two searches:

  • Equality then range — "every Smith whose first name is from D to M." Jump to Smith, then walk a span from Dan to M. Both columns do real work. ✓
  • Range then equality — "everyone from A to M whose first name is Eve." You walk a huge span of last names, and inside that span first names aren't in order — so "Eve" can't help you skip anything. Only the last-name range is used. ✗

Generalize that and you get the rule. A range condition is >, <, >=, <=, BETWEEN, LIKE 'x%', or IN (...) — anything that matches a span of the index rather than one value.

The ruleIn a composite index, MySQL can use equality columns up to the first range. The range column itself is used; every column after the first range is not used to narrow the search. MySQL docs — "Multiple-Column Indexes"

key_len: your ruler for the prefix

How do you know how many columns are being used? The key_len column of EXPLAIN reports the length of the index key actually used, in bytes. More columns used → bigger key_len. For INT UNSIGNED NOT NULL each column is 4 bytes, so:

key_lenMeaning for index (store_id, amount)
4Only store_id is used.
8Both store_id and amount are used.

key_len is the objective proof of the leftmost-prefix and range rules — no guessing about whether a column "counts."

Do it on your machine

Small table this time — EXPLAIN reports the plan regardless of row count, so we don't need 100,000 rows to see the difference.

1. Create the table and index

CREATE TABLE sales (
  id       INT UNSIGNED NOT NULL AUTO_INCREMENT,
  store_id INT UNSIGNED NOT NULL,
  amount   INT UNSIGNED NOT NULL,
  PRIMARY KEY (id),
  KEY idx_store_amount (store_id, amount)
) ENGINE=InnoDB;

2. Fill it with 500 rows

SET SESSION cte_max_recursion_depth = 1000000;

INSERT INTO sales (store_id, amount)
WITH RECURSIVE seq (n) AS (
  SELECT 1
  UNION ALL
  SELECT n + 1 FROM seq WHERE n < 500
)
SELECT (n % 10) + 1, (n * 13) % 500 + 1
FROM seq;

3. Watch key_len as you add columns

-- equality on the leftmost column only
EXPLAIN SELECT * FROM sales WHERE store_id = 5;

-- equality, then a range → both columns used
EXPLAIN SELECT * FROM sales WHERE store_id = 5 AND amount > 100;

-- range, then equality → only store_id is used
EXPLAIN SELECT * FROM sales WHERE store_id > 5 AND amount = 100;

Expected:

WHERE clausetypekey_lencolumns used
store_id = 5ref4store_id
store_id = 5 AND amount > 100range8store_id + amount
store_id > 5 AND amount = 100range4store_id only

The third row is the whole lesson: amount = 100 is an equality, but it sits after a range on store_id, so MySQL can't use it to narrow the scan. key_len stays at 4. The amount = 100 still gets applied — but as a filter on rows already located, not as part of the index seek.

One nuance: ININ (5, 6, 7) is a range (several values), but it can be followed by more columns — unlike >. So WHERE store_id IN (5,6) AND amount = 100 uses both. IN behaves like a multi-value equality, not an open-ended range.

Self-check

Answer from memory — don't scroll up.

With index (a, b), WHERE a = 1 AND b > 5 uses…

Equality on a, then a range on b — both are used, because the range comes after the equality.

With index (a, b), WHERE a > 1 AND b = 5 uses…

b sits after a range on a, so it can't narrow the seek — it becomes a filter on rows already found.

In EXPLAIN, key_len tells you…

key_len is the byte length of the index key used — the objective count of how many prefix columns the query actually consumed.
