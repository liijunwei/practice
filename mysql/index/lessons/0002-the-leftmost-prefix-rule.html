MySQL Indexes · Lesson 2

A composite index is sorted like a phone book

An index on (a, b) is sorted by a first, then by b — exactly like a phone book: last name, then first name. That ordering is the whole game. It means you can search from the left, but never skip the left. This is the leftmost-prefix rule, and it decides whether your composite index actually helps.

The win

By the end you'll (1) state the leftmost-prefix rule in one sentence, (2) predict which WHERE clauses can use a composite index, and (3) add the index that filters and sorts a query — turning a full scan with a sort into a lookup with none.

The mental model: a phone book

Last lesson an index was a sorted copy of one column. A composite index (a multi-column index) is a sorted copy of several columns — sorted by the first, then the second, then the third. Picture a phone book:

last_namefirst_name
AdamsAlice
AdamsBob
SmithCarol
SmithDan
SmithEve
YoungFrank

Sorted by last_name; and within the same last name, sorted by first_name. Two consequences fall straight out of this:

  • All the "Smith"s are together — so you can jump straight to them by last name.
  • The "Smith"s are already in first-name order — so if you want Smiths sorted by first name, it's free.

But notice what you can't do: jump to "everyone named Eve." The book isn't sorted by first name, so Eve lives scattered across Adams, Smith, Young… To find all Eves you'd have to read the whole book.

The ruleA composite index (a, b, c) can serve a lookup only if your equality conditions use its columns from the left: a, or a,b, or a,b,c. It can never serve b alone, or b,c, because the entries aren't sorted that way. That's the leftmost-prefix rule. MySQL docs — "Multiple-Column Indexes"

Which clauses can use it

For an index on (customer_id, created_at):

WHERE clauseUses the index?
customer_id = 7✓ leftmost prefix
customer_id = 7 AND created_at = '…'✓ full prefix
created_at = '…'✗ skips the leftmost
created_at = '…' AND customer_id = 7✓ order doesn't matter

That last row is worth saying out loud: the optimizer doesn't care how you write your equality conditions — it reorders them. What it cares about is whether the leftmost column is present. So WHERE created_at = '…' AND customer_id = 7 uses the index just fine, while WHERE created_at = '…' alone cannot.

The payoff: filtering and sorting in one shot

Here's the query that makes column order matter in production — "a customer's most recent orders":

SELECT * FROM orders
WHERE customer_id = 7
ORDER BY created_at DESC
LIMIT 10;

With no index, MySQL must (a) read every row to find customer 7's, then (b) sort those rows by created_at. That second step shows up in EXPLAIN as Using filesort — the telltale sign of a sort MySQL has to do itself. With an index on (customer_id, created_at), both steps vanish: it jumps to customer 7's entries, and they're already in created_at order. Same trick as the phone book — the Smiths come pre-sorted by first name.

Do it on your machine

Fresh table this time (the people table from last lesson is still around if you want to compare). We'll make 100,000 orders across 50 customers.

1. Create the table

CREATE TABLE orders (
  id          INT UNSIGNED NOT NULL AUTO_INCREMENT,
  customer_id INT UNSIGNED NOT NULL,
  created_at  DATETIME     NOT NULL,
  amount      INT UNSIGNED NOT NULL,
  PRIMARY KEY (id)
) ENGINE=InnoDB;

2. Fill it with 100,000 rows (2,000 per customer)

SET SESSION cte_max_recursion_depth = 1000000;

INSERT INTO orders (customer_id, created_at, amount)
WITH RECURSIVE seq (n) AS (
  SELECT 1
  UNION ALL
  SELECT n + 1 FROM seq WHERE n < 100000
)
SELECT
  (n % 50) + 1,                                  -- customer_id 1..50
  TIMESTAMP('2020-01-01') + INTERVAL n MINUTE,   -- spreading dates
  (n * 7) % 900 + 1
FROM seq;

3. Run the slow query — no index yet

EXPLAIN SELECT * FROM orders
WHERE customer_id = 7
ORDER BY created_at DESC
LIMIT 10;

Expected: type = ALL, key = NULL, and in the Extra column, Using filesort. MySQL reads all 100,000 rows and sorts them to find 10.

4. Add the composite index, re-check

CREATE INDEX idx_cust_created ON orders (customer_id, created_at);

EXPLAIN SELECT * FROM orders
WHERE customer_id = 7
ORDER BY created_at DESC
LIMIT 10;

Now the plan flips. Expected:

typekeyExtra
no indexALLNULLUsing filesort
with indexrefidx_cust_created(no filesort)

The Using filesort is gone because the index hands back customer 7's rows already ordered by created_at. Same answer, no sort.

5. Now test the leftmost-prefix rule

Run each and check the type / key:

-- full prefix: both columns  → uses idx_cust_created
EXPLAIN SELECT * FROM orders WHERE customer_id = 7 AND created_at = '2020-01-05';

-- leftmost only: first column  → uses idx_cust_created
EXPLAIN SELECT * FROM orders WHERE customer_id = 7;

-- skips the leftmost  → type=ALL, ignores the index
EXPLAIN SELECT * FROM orders WHERE created_at = '2020-01-05';

The third one is the lesson in miniature: created_at is the second column, so it can't be searched on its own. The index is only sorted by created_at within each customer, never globally. MySQL falls back to a full scan.

Self-check

Answer from memory — don't scroll up.

An index on (last_name, first_name) is sorted by…

Sorted by the first column; the second is only the tie-breaker — like last name, then first name.

With index (customer_id, created_at), which filter can't use it?

created_at alone can't be used because it isn't the leftmost column — the index is only sorted by it within each customer.

With index (customer_id, created_at), which query avoids a filesort?

Filtering on customer_id and sorting by created_at matches the index order exactly, so rows already come out sorted.
